# 后续验收与发布计划（2026-09-21）

状态：本文件只定义后续工作，不在本轮修复实现。当前提交保留现有 Hybrid Mount 与 WebUI 第一轮改动，发行包明确标注温控阈值修改风险。

## 计划 A：Hybrid Mount 温控事务安全化

### 目标

将 thermal 与 UECap 的修改从“运行期改 active module source”改成“pending profile + 重启前 promotion + 启动后复读 + A/B 回滚”。在完成全部门禁前，Hybrid Mount 下禁止 WebUI 直接写入 `system/vendor`。

### 不变量

1. Hybrid Mount active 期间不修改 `/data/adb/modules/pixel9pro_control/system/vendor/**`。
2. WebUI 只写模块私有 data/pending 区，候选内容使用临时文件、`fsync`、原子 rename。
3. Thermal JSON 必须通过 JSON 解析、设备/Build 基线、HotThreshold 严格递增、`previous <= next - next_hysteresis`、`"NAN"` 字符串和完整配对文件检查。
4. 通过 `vendor_configs_file`、`vendor_fw_file`、0644、owner/group 和 source hash 复读后才能提交 pending manifest。
5. active slot、pending slot、effective `/vendor` 三者必须有独立 hash；任何 mismatch 都保持旧 slot 或 stock。

### 实施阶段

#### A0：止血门禁

- Hybrid backend 下暂时拒绝 thermal custom mutation，返回 `409` 与 `reboot_required=false`。
- `cmd thermalservice override-status` 只能作为诊断命令，不作为温控档位持久化接口。
- `post-mount` 发现 source/effective mismatch 时写入 rollback marker，不继续声称 verified。

#### A1：Pending profile

- 新增 `/data/adb/pixel9pro_control/pending/thermal/` 和 `/data/adb/pixel9pro_control/pending/uecap/`。
- 每个候选包含内容 hash、设备、Build、SELinux context、权限、父 manifest hash 和创建 boot id。
- WebUI 事务顺序固定为：锁 → 生成 → 校验 → fsync → 原子提交 manifest → 返回 `pending_reboot`。

#### A2：A/B slot

- 为 thermal/UECap 各维护 `slot-a`、`slot-b`、`active`、`pending`、`last-good`。
- 只在 inactive slot 生成内容；active slot 永远只读。
- 两次连续启动通过 effective readback 后才清理旧 slot。

#### A3：Pre-mount promotion

- 通过项目专用 MetaModule 或可信的模块更新 promotion 在 Hybrid Mount 扫描前切换 source。
- 不在 `service.sh` 或 late-start 阶段复制到 `/vendor` 或 active lower layer。
- 明确 APatch、KernelSU、Magisk 的 promotion 入口与失败回滚入口。

#### A4：Boot readback 与回滚

- 在 Thermal HAL 读取配置前完成静态合同检查。
- 挂载后复读 source/effective hash、context、mount backend 和 Hybrid `state.json`。
- 复读失败时保留 last-good，下一次启动自动回滚；receipt 必须标记 `rollback_pending` 或 `verified`，禁止模糊成功。

### A 验收门禁

- system → custom、custom → custom、custom → system、重启中断、重复点击、断电、旧 slot 残留均有 fixture。
- caiman APatch + Hybrid Mount 连续冷启动至少 3 次。
- Hybrid OverlayFS、Magic Mount、VFS 分别证明路径策略；VFS 不得伪装为真实 mount。
- `thermalservice`、`vendor.thermal-hal`、`dumpsys thermalservice`、`/vendor` hash/context、Hybrid state 和 receipt 形成同一证据包。
- 任何一次第二屏、Thermal HAL crash loop 或 hash/context mismatch 都判定未通过。

## 计划 B：12 文件 UI 第一轮改动完整校验

### 范围

当前 UI/telemetry 改动涉及分析页、诊断页、后台日志、采样接口、CSS 和缓存版本。先校验行为合同，再做浏览器和真机验收；本轮不扩展产品功能。

### 静态与接口合同

1. 对 `analytics.js`、`analytics_model.js`、`analytics_view.js`、`capture.js`、`diagnostics.js`、`index.html` 执行 Node syntax/加载顺序检查。
2. 对 `telemetry.sh` 执行 Shell syntax、输入边界、最近 1–7 天限制、hour/minute bucket、空数据和跨天边界 fixture。
3. 验证无有效功耗差分时不画曲线、不制造 0 值假线；充电中段、负差分、单点和全空窗口均显示明确状态。
4. 验证软件耗电排行的来源、Top N 排序、系统分项、未知包名、空归因和后台快照未完成状态。
5. 验证后台日志导出脱敏、下载文件名、清除动作位置、失败提示和重复点击锁。

### 浏览器复核

- 375、768、1280px 视口；浅色/深色；中文长文案；无横向溢出。
- 温度五档区间保持单行优先；自定义区间只显示 1–7 天和小时/分钟；无有效差分不显示假曲线。
- 统计页切换、收起/展开、来源切换、后台刷新、超时、取消和页面隐藏恢复后无重复请求或旧请求覆盖新状态。
- 运行记录、错误详情、日志导出和清除按钮在可访问名称、焦点顺序和键盘操作上通过。

### 真机与打包

- API 返回值、WebUI 状态和实际 `.logs`/Download 文件一致。
- 确定性双构建 hash、entry 数量、WebUI cache stamp、权限和路径审计一致。
- UI 验收不得改变当前温控风险结论；Hybrid thermal custom 仍保持禁用/警告状态。

## 计划 C：RC 发布与警告边界

- RC 只上传当前设备最后一份候选 ZIP，不宣称稳定版。
- 唯一发行警告：`APatch/KernelSU + MetaModule 下温度阈值修改存在已知风险；Magisk 运行期修改也不宣称安全，只有离线更新并重启才进入可验证路径。`
- 发布说明必须附带曲线救国步骤：卸载 Pixel 9 Pro Control → 重启 → 重新安装 ZIP → 向导选择新配置 → 再重启 → 检查 receipt、`/vendor` hash、SELinux context。
- RC 不得隐藏 Hybrid thermal custom 未通过的事实，不得把 framework thermal status override 当成配置生效证明。
